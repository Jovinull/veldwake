# Known issues and limitations

Last updated: 2026-09-17

| ID | Status | Issue | Consequence / next action |
|---|---|---|---|
| KI-001 | Open | `Veldwake` is only a working title; preliminary transcript research is not legal clearance. | Perform formal INPI/USPTO/EUIPO, store, domain, and counsel review before public branding. |
| KI-002 | Open | The only executable is a Windows-first diagnostic renderer, not a playable game; other OSes/backends are unverified. | Expand support only when a milestone has a concrete target and validation host. |
| KI-003 | Open | Integrated GPU and shared memory make the audit host useful as a conservative dev target, not a complete hardware matrix. | Add discrete-GPU and lower-end CI/manual test coverage later. |
| KI-004 | Open | Vulkan loader reports an OBS hook layer older than the requested Vulkan API and a missing layer-manifest registry lookup. | D3D12 remains the primary Windows path; reassess only if Vulkan testing becomes required. |
| KI-005 | Open | No project license is selected. | Owner decision required before public distribution/contributions. |
| KI-006 | Open | M1 through M4 have one-host visual validation but no automated visual regression or multi-adapter coverage. M4 adds named camera poses and locked content fixtures, which make two captures comparable, but nothing compares them automatically and no second adapter has been tested. | Add stable capture fixtures and broader hardware coverage when rendered game content begins to change. M4's `region::GOLDEN_POSES` is the anchor a future comparison would use; a pixel comparison is deliberately not the oracle, because a driver change would break it without a voxel moving. |
| KI-007 | Accepted | `cargo-deny` reports transitive duplicate pairs for `hashbrown` and `syn` in the current `wgpu` graph. | Keep duplicate visibility as a warning; reassess on dependency upgrades rather than forcing transitive versions. |
| KI-008 | Open | The audited Windows host has intermittently produced linker `LNK1104` for test executables when `cargo nextest` follows another Cargo gate, even sequentially. Recurred twice on 2026-09-16 during M3B work and twice consecutively during M3C0 (no holder process, files absent); the third plain run and a `--build-jobs 1` run both passed 86/86. During M3C1 it failed four consecutive times (including `--build-jobs 1`) before passing; a bounded retry loop of five plain runs is now the working procedure. | Verify no project/Cargo process is holding the named executable, then rerun `cargo nextest` alone (a bounded loop of up to five plain runs, stopping at the first run without `LNK1104`). This retry applies only to the linker/host lock: an assertion failure, panic, failing test, Clippy or build error, or any other gate result is evidence and must never be re-run until it passes. Do not clean artifacts or change code unless the isolated retry also fails. |
| KI-009 | Accepted | (a) Presentation-only invalidations — a level change of the chunk or a neighbor, render-membership churn — used to stop an already drawn mesh until its replacement was meshed and uploaded; on the M3C2 path this opened 909 gaps of up to 232 frames with 62 chunks missing at once. (b) Data invalidations still stop stale geometry immediately. | (a) Resolved by retaining the committed mesh until a seam-coherent group commit: current QA recorded zero gaps where previously drawn meshes disappeared and zero mixed-seam invariant failures. This does not cover never-drawn frontier entrants; KI-014 tracks those separately. (b) Accepted by design: never draw data that is gone/unproven or turn an unavailable neighbor into AIR. |
| KI-011 | Open | Transition groups are connected sets of changing seams and are unbounded (78 chunks observed at the corridor start); while the camera keeps crossing the band the `Lod0` ring's group is re-dirtied before it commits, so drawn chunks can keep a coherent but stale level until the camera slows. | Never a hole or a mixed seam; converges at rest (`transition_pending = 0`). Now directly observable: the M3C3 `Boundaries` view draws every uncommitted group member in violet and switches to red at 16 members, and the driven smoke shows large groups persisting across a traversal. Measure `blocked_group_max` and `constrained_undrawn_*` in the swap-churn investigation; bound groups only with a proof that a partial commit cannot expose a mixed seam. |
| KI-012 | Accepted | The debug views allocate one uniform buffer, one bind group, and one draw call per primitive. Measured on the audited host with an idle camera: 637 residency boxes take the client from 60 FPS to 37.6 and then 15.4 FPS (26.6 ms, then 64.8 ms per frame); 180 boundary primitives give 46.7–47.9 FPS. | Deliberate diagnostic pattern. In `Off`, current instrumentation reports zero per-frame debug primitive allocations, uniform writes, and draws, with mesh upload budget unchanged. Fixed startup pipeline/unit geometry and slots retained after prior use still consume resources; “off” never meant zero fixed residency. Do not add batching/render graph without a milestone need. |
| KI-013 | Open | LOD's chunk-mesh memory benefit against the **diagnostic fixture** is much smaller than M3C2 reported. Mutation-boundary sampling (including after stage and before commit) gives a peak simultaneous presentation-owned chunk-mesh total of 12,101,888 → 10,053,696 (−16.9%), while upload bytes rise 81.6%. The banded peak is run-dependent: five later runs of the identical path measured 9,734,816 to 9,800,128 (−19.0% to −19.6%), so the saving is a range and a single sample is not reproducible. This is not global GPU memory. | Earlier −57%/−59% counted committed buffers only; the later −19% figure still sampled only at update end and missed intra-update overlap. LOD stays opt-in. Future claims must use mutation-boundary simultaneous totals and separately account for depth, pipelines, debug resources, and driver/wgpu retention when global GPU memory matters. M4 measured a much larger saving against real terrain — 21,806,552 against 65,992,424 settled chunk-mesh bytes at the same camera, −67% — but that is settled committed bytes at one pose, not a simultaneous peak over a traversal, and the two numbers must not be compared as if they measured the same thing. |
| KI-014 | Open | A zero “previously drawn gap” count does not prove complete frontier coverage. On the QA banded path, up to two non-empty CPU-ready chunks were staged but temporarily withheld by their seam-coherent transition group (15 updates, 21 chunk-frames); historical debug smoke reached 13 but lacked cause attribution. | Treat non-zero `ready_undrawn` as a real temporary coverage hole, even when seam-safe and bounded. Preserve the split metrics (`frontier_pipeline_pending`, `ready_awaiting_upload`, `ready_blocked_transition`, `committed_missing`). Investigate alongside KI-011; never claim “zero holes” from `gaps_closed = 0` or a few visually continuous captures. |
| KI-015 | Open | The M3D disk cache has no eviction or size policy. A changed format/source identity uses another directory, leaves earlier identities on disk, and nothing bounds total growth. Cold `ChunkCache::open` walks the current identity synchronously, so a very large opt-in cache can also lengthen startup. | Deliberate for an experiment: footprint is reported explicitly and `ChunkCache::clear` removes one identity's entries. Production needs size/age policy, sharding/region layout, and a decision about asynchronous startup against real world generation. No directory scan occurs per frame. |
| KI-017 | Open | Settling the M4 golden profile takes about a minute (59.7 s on the audited host for 3,211 loads and 351 meshes). The runtime dispatches at most one worker job per `poll` and `poll` runs once per frame, so at 60 Hz throughput is bounded at roughly sixty jobs per second whatever the worker can do. Most of those jobs resolve to authoritative absence: the demand set is a cube 13 chunks tall while the region is 3. | Not a rendering cost and not a correctness problem: every capture settles, and the counters stay clean. Two independent avenues if it ever matters — dispatch more than one job per poll, and stop spending a load on coordinates a source could reject from its extent alone. Neither belongs in M4; both need their own evidence. |
| KI-016 | Open | On the **diagnostic fixture** the cache is slower than regeneration. The original three-run set measured warm at 13–37 ms versus 6–7 ms cacheless; after QA removed an accidental maximum-size reservation per read, the final sample measured raw warm at 15–17 ms versus 5 ms and RLE warm at about 8 ms versus 4 ms. The source is trivial and timings are noisy, but no run demonstrates a benefit. | Scoped to the diagnostic source by M4 evidence. Against real terrain generation the cache is clearly worth having: a warm run of the same 81 chunks reaches idle in 11 ms where regeneration takes 68. The entry remains open because the cache is still opt-in and still an experiment, and because the diagnostic finding stands as written for that source. |
| KI-010 | Closed | M3B2 initially lacked visual verification of seams, unloaded-as-AIR, re-entry, and window lifecycle. | Closed 2026-09-16 by the driven Windows/D3D12 smoke recorded in `planning/M3_STREAMING_WORLD.md`: scripted traversal with screenshot inspection, re-entry, resize, minimize/restore, focus loss, and Escape all verified on the audited host. The transient invalidation blink is log-evidenced only, and coverage remains one integrated-GPU host (KI-003, KI-006). |
